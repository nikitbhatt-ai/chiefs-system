## Executive summary (read this first)

**P0 findings: 8. P1 findings: 9.**

The accounting module is genuinely well built at the ledger layer — integer cents everywhere, DB-enforced balance and immutability triggers, reversal instead of edit, FIFO subledger reconciliation. That foundation is sound. The problems are almost entirely at the **seams** where the operational side of the app hands money to the accounting side.

Three things are costing real money right now:

1. **Receiving a PO and then entering the vendor's bill books the same cost twice and Accounts Payable twice.** There is no goods-received-not-invoiced clearing account in the chart of accounts, so both events credit account 2000 directly.
2. **Saving a quote a second time silently sets its sales tax to $0.** The tax rate the rep typed is never stored anywhere, and the save action recomputes tax from the (always-blank) form field.
3. **Syncing an upfit configuration onto a quote re-prices every part line at today's price list**, overwriting the agreed price — including on quotes that have already been invoiced.

Separately: the entire vehicle side of the business (buying a vehicle, reconditioning it, selling it) has **no code path into accounting at all**, and neither does labor-per-job. `vehicles.purchase_price` is a column nothing ever writes.

Report continues below in the requested order.

# Part 2 — Non-functioning buttons and controls

## 2.0 A correction to the audit criteria

The prompt asks me to judge mutations against react-query `invalidateQueries`. **This app does not use react-query.** `@tanstack/react-query` is declared at `package.json:22` but appears in zero source files — the only match across `src/` is the package.json line itself. The app is server components + server actions + `revalidatePath`, with client forms using `router.refresh()`.

So I applied the equivalent test instead: **does the write path call `revalidatePath` (server action) or `router.refresh()` (client fetch)?** Judged that way, refresh-after-write is handled correctly essentially everywhere I checked.

## 2.1 Categories that came back clean

I want to be explicit about what I did *not* find, because it changes where the fix effort should go:

- **No handler / empty handler / `console.log` handler / TODO stub: zero instances.** A full-tree grep for `TODO`, `FIXME`, `console.log`, `@ts-ignore`, and `@ts-expect-error` across `src/` returns **nothing**.
- **Placeholder navigation (`href="#"`, `href=""`): zero instances.**
- **Buttons with neither `onClick` nor `type="submit"`: 4 candidates, all actually wired.** Three are the print buttons at `src/app/quotes/[id]/print/page.tsx:240`, `src/app/inventory/print/page.tsx:144`, and `src/app/deals/[id]/documents/[kind]/print/page.tsx:35`, all bound imperatively by a `PrintTrigger` client component (`src/app/quotes/[id]/print/PrintTrigger.tsx:5-13`) that is rendered on each of those three pages (`:172`, `:94`, `:34`). The fourth (`src/app/settings/sla/page.tsx:105`) uses `formAction={resetSla}`, which is valid.
- **No pending state on the money forms: not an issue.** `BillForm.tsx:54,223`, `PaymentForm.tsx:41,~200`, `ReceiptForm.tsx:44,~215`, and `IssueInvoiceForm.tsx:28,~110` all hold a `busy` flag and set `disabled={busy || …}`.
- **No `onError` on the money forms: not an issue.** All four surface `data.error` into a visible red panel and catch network failures separately.

The broken controls in this app are all in two categories: **silent permission dead-ends** and **silent failures**.

| Bill lines | `Math.round(line.amountCents ?? 0)` — `src/lib/ap.ts:88`, `:114`, `:152` | **Per line.** Correct. |

| Labor cost (timeclock) | `Math.round(hours * 95 * 100) / 100` — `src/lib/timeclock.ts:138` | Per work order. |
| Inventory subledger valuation | `ROUND(unit_cost * 100)` in SQL — `src/lib/inventoryValuation.ts:23`, `:51` | Per FIFO layer. Correct. |

**Verdict.** The accounting module rounds per line, consistently, and is safe. The **quote and PO documents round only at the total**, so line amounts persisted in jsonb are unrounded doubles and `Σ round(line) ≠ round(Σ line)` in the general case. A quote with three lines at `1 × 10.005` stores `subtotal = "30.02"` (`30.014999… → 30.01`, in fact — the exact `.toFixed` result depends on the binary representation) while the three displayed line totals each read `$10.01` and visibly sum to `$30.03`. Magnitude is sub-cent per line, but it makes an invoice total disagree with the sum of its printed lines, which is exactly the symptom the question is about.

### PO-specific verifications

**Three-way match (PO qty/price vs received vs billed):** **No.** All three numbers exist in the database — PO line `quantity`/`unitCost` in `purchase_orders.line_items`, received quantity in `purchase_orders.line_items[].quantityReceived` and in `part_receipts`, billed amount in `bills`/`bill_lines` — but **no code joins them.** There is no matching function, no variance report, and no screen showing the three side by side. `bills.purchase_order_id` is the only structural link, and it is never populated by the UI (see below). Overbilling is not detectable by the system.

**Over-receipt (receive 12 against a PO for 10):** **Silently clamped, not blocked and not warned.** `src/lib/inventory.ts:219-220` computes `remaining = quantity − quantityReceived` and then `qty = Math.max(0, Math.min(receiveNow, remaining))`. The UI also sets `max={remaining}` on the input (`POEditor.tsx:248`) but that is a client hint only. So the extra 2 units are discarded with no message. The physical situation (12 units on the dock, 10 in the system) is unrecoverable through this screen.

**Duplicate posting:**
- *Receive clicked twice:* **Protected.** The PO row is locked `FOR UPDATE` (`src/lib/inventory.ts:206`) and line quantities are re-read inside the transaction, so the second submit sees `remaining = 0`, clamps to `qty = 0`, skips the layer insert and the on-hand bump, computes `receivedCents = 0`, and `postInventoryReceipt` returns early at `inventoryLedger.ts:39`. Correctly idempotent. The design intent is documented at `src/lib/inventory.ts:15-17`.
- *Same vendor bill entered twice:* **Not protected.** `bills.vendorInvoiceNumber` (`src/db/schema.ts:856`) has **no unique constraint** and no application-level duplicate check in `createBill` (`src/lib/ap.ts:95-160`). Entering the same vendor invoice number twice creates two bills, two AP credits, and two expense debits. No idempotency key exists on any accounting write.
- *Related:* `nextNumber` uses `count(*) + 1` (`src/lib/ap.ts:54-57`, `src/lib/ar.ts:76-79`), which under concurrency collides against the `unique` constraint, and after any void can reuse an already-used number permanently.

**PO-to-job linkage:** **Not possible.** `purchase_orders` has **no `work_order_id` column** (`src/db/schema.ts:322-336`). Parts bought for a specific job land in general Inventory and only reach the job later, when `consumeWorkOrderParts` issues them to WIP. Vendor bills *could* be attributed to a job — `bill_lines.work_order_id` exists (`src/db/schema.ts:882`) and the API accepts it (`api/accounting/bills/route.ts:33`) — but **`BillForm.tsx:87-94` never sends it**, nor does it send `purchaseOrderId`. Through the only UI the app provides, every bill is unattributed to both a PO and a job.

**Customer POs vs vendor POs:** **Cleanly separated — no dangerous mixing.** `purchase_orders` is vendor-only: it has `vendor_id` and no `customer_id` (`src/db/schema.ts:327`). A government customer's PO *to us* is handled on the CRM side as a deal stage (`deal_stage` includes `po_received`, `src/db/schema.ts:21`) and as an uploaded document (`customer_documents.kind`, `:430`). The two concepts never share a table or a numbering series. ✅

## 4.3 Money that currently goes nowhere

Plain English. Every dollar event with no path into accounting at all.

1. **Buying a vehicle.** What you paid a dealer or an auction for a truck is not recorded anywhere. The column exists (`vehicles.purchase_price`) and no screen or API writes it. No vehicle-inventory asset account exists in the chart of accounts.
2. **Reconditioning a vehicle.** No field, no table, no code. Recon spend is invisible.
3. **Selling a vehicle.** `vehicles.status` can be set to `sold` and `list_price` is used to publish to Shopify (`src/lib/publishVehicle.ts:56`), but no sale is ever booked. No revenue, no cost relief, no gain or loss.
4. **Technician labor on a job.** Hours are captured accurately. Their cost is calculated on two screens (at two different rates) and posted to the ledger by neither. WIP contains materials only, so every job's ledger cost understates the truth by its entire labor content, and gross margin on any upfit is wrong.
5. **Sublet and outside service work.** No concept in the schema or the code. Can only be captured as a hand-typed bill line to a generic expense account, unattributed to any job.
6. **Committed spend on open purchase orders.** POs correctly stay off the ledger, but no dollar figure of open commitments is tracked anywhere, on a job or in total. Procurement counts quantities only.
7. **PO-to-bill price variance.** Overbilling by a vendor is undetectable — nothing compares what was ordered, what arrived, and what was billed.
8. **Discounts given.** Computed on every quote and thrown away. Revenue is booked net, so total discounting is unmeasurable.
9. **Fees charged.** Same — rolled into the taxable base and lost as a separate figure.
10. **Customer deposits.** The CRM has a `deposit_received` stage and a deposit-receipt document template, but no deposit amount is ever recorded and no customer-deposits liability account exists. Cash arriving before an invoice has nowhere to land except as an on-account receipt against AR.
11. **Tax exemption on government sales.** `customers.tax_exempt` is captured and shown to users, and read by no tax logic. Nothing distinguishes an exempt sale from a taxable one anywhere in the books.
12. **Value destroyed by deleting a part.** Deleting a part cascades away its FIFO layers. The inventory subledger drops by that value; GL 1200 does not. No journal entry, no warning, no permission check.
13. **Sales tax that was charged but zeroed by a re-save.** Every quote re-save through the main editor writes `tax_total = 0`. If the invoice is issued after that, the tax liability is never credited to 2100 and the tax was collected — or not collected — off the books. (This is a defect, listed here because its effect is money with no accounting path.)

# Part 6 — Ranked fix plan

Ranked strictly by financial risk. Grouped into batches you can approve one at a time. Time estimates assume one focused developer session each and exclude the Neon SQL you would run by hand.

## P0 — Money is silently wrong, lost, or double-counted

### Batch A — Stop the double-count (do this first, alone)

**A-1. PO receipt and vendor bill both credit Accounts Payable.**
*What is wrong:* Receiving goods posts Cr AP 2000 (`src/lib/inventoryLedger.ts:50`); entering the vendor's bill posts Cr AP 2000 again (`src/lib/ap.ts:119`). AP is overstated by the value of every received-and-billed PO, and the cost is recorded twice — once as an Inventory asset, once as an expense debit.
*Files:* `docs/sql/accounting_phase1.sql` (new account), `src/lib/inventoryLedger.ts:31,50`, `src/lib/ap.ts:28-31,112-119`, `src/components/accounting/BillForm.tsx`.
*Smallest safe fix:* Add one GL account — `2050 Accrued Purchases (GRNI)`, liability, credit-normal, `report_group = 'none'`. Change `postInventoryReceipt` to credit `2050` instead of `2000`. Add a PO picker to `BillForm` so a bill against a PO debits `2050` (relieving the accrual) rather than a hand-picked expense account; leave non-PO bills exactly as they are.
*Time:* ~4 hours, plus a one-time correcting journal entry for whatever has already double-posted.
*What could break:* Any existing balance in AP 2000 that came from a receipt is now misclassified. **Do not deploy without first running the AP aging report (`/accounting/reports/ap-aging`) and the 2000 account ledger (`/accounting/reports/ledger/2000`) to size the existing error**, then correct it with a reversing entry. The balance sheet will move.

### Batch B — Quote money integrity (three fixes, one migration)

**B-1. The quote's tax rate is not stored, so every re-save zeroes the tax.**
*What is wrong:* `QuoteEditor.tsx:77` initialises `taxRate` to `"0"` and never hydrates it from the quote — because there is nowhere to hydrate it from. `saveQuote` (`quotes/[id]/page.tsx:60-63`) then recomputes `taxTotal` from that blank field. Open a taxed quote, change a note, save: the tax is gone and `grand_total` drops. The upfit path already works around this by back-deriving the rate (`upfit/page.tsx:151-156`), which proves the gap was known.
*Files:* `src/db/schema.ts:215-242`, `src/app/quotes/[id]/page.tsx`, `src/app/quotes/[id]/QuoteEditor.tsx`, `src/app/quotes/[id]/upfit/page.tsx`.
*Smallest safe fix:* `ALTER TABLE quotes ADD COLUMN tax_rate_pct numeric(6,3) NOT NULL DEFAULT 0;` — you run this in Neon. Pass it into `QuoteEditor` as `initialTaxRate`, persist it in `saveQuote`, and delete the back-derivation in the upfit path.
*Time:* ~2 hours.
*What could break:* Existing quotes get `tax_rate_pct = 0` while carrying a non-zero `tax_total`. Backfill with `tax_rate_pct = round(tax_total / (grand_total - tax_total) * 100, 3)` where the denominator is positive, and eyeball the results before trusting them.

**B-2. Syncing an upfit re-prices every part line at today's price list.**
*What is wrong:* `generateQuoteFromUpfit` (`upfit/page.tsx:108-120`) discards the agreed `unitPrice` on every item line and rebuilds it from `parts.price` as of now. A quote agreed at last month's prices is silently repriced — including a quote that has already been invoiced.
*Files:* `src/app/quotes/[id]/upfit/page.tsx:108-125`.
*Smallest safe fix:* Match incoming pins against existing item lines by `partId` and preserve the stored `unitPrice`, `discount`, and `discountKind` on any line that already exists; take `parts.price` only for genuinely new lines. Refuse the whole operation when an `ar_invoices` row exists for the quote.
*Time:* ~3 hours.
*What could break:* Reps who currently rely on this to refresh stale pricing lose that behavior. Give them an explicit "re-price from current list" button instead of making it a side effect.

**B-3. A quote is fully editable after its invoice has posted, and the invoice PDF reads the live quote.**
*What is wrong:* `saveQuote` never checks `ar_invoices` (`quotes/[id]/page.tsx:14-107`), and `resolveQuote` renders live quote data for `variant=invoice` (`pdf/registry.tsx:29-53`, served by `api/pdf/quotes/[id]/route.ts:21-25`). The document you hand the customer and the amount in the ledger diverge with nothing flagging it. The PDF does not even show the `INV-nnnn` number.
*Files:* `src/app/quotes/[id]/page.tsx`, `src/app/quotes/[id]/upfit/page.tsx`, `src/lib/pdf/registry.tsx:29-53`, `src/lib/pdf/templates/quote.tsx`.
*Smallest safe fix:* In both write paths, look up `ar_invoices` by `quote_id` and refuse the save with a clear message when one exists. In `resolveQuote`, when `variant === "invoice"`, read totals and the invoice number from `ar_invoices` rather than from `quotes`.
*Time:* ~4 hours.
*What could break:* Legitimate post-invoice corrections stop working, which is the point — they should go through void-and-reissue. Confirm that flow is usable before shipping the lock.

### Batch C — Rate and amount integrity

**C-1. Two competing labor cost rates that disagree; one defaults to zero.**
*What is wrong:* `src/config/labor.ts:4` hardcodes `$95/h`, read by `src/lib/timeclock.ts:138` and shown on the work-order page (`work-orders/[id]/page.tsx:178-179`). `src/lib/jobCosting.ts:107-113` uses the `labor_rates` table, which returns `0` when unseeded (`:36`). Same job, same hours, two different labor costs on two screens.
*Files:* `src/config/labor.ts`, `src/lib/timeclock.ts:10,138`, `src/app/work-orders/[id]/page.tsx:12,178-179`.
*Smallest safe fix:* Make `labor_rates` the single source. Have `laborByWorkOrder()` take rates from `laborRateMap()`/`defaultLaborRateCents()`, delete `src/config/labor.ts`, and seed the shop default row to 9500 cents so behavior is unchanged on day one. Show "rate not set" rather than `$0.00` when the default is missing.
*Time:* ~2 hours.
*What could break:* If the `labor_rates` default row is not seeded first, every labor figure drops to $0. **Seed the row before deploying**, and verify at `/accounting/labor-rates`.

**C-2. Receipts and payments accept overpayment with no cap and no warning.**
*What is wrong:* Neither `recordReceipt` (`src/lib/ar.ts:174-238`) nor `recordPayment` (`src/lib/ap.ts:175-236`) compares the amount to the open balance. A $10,000 receipt against a $1,000 invoice marks it `paid` (`ar.ts:254`) and drives AR contra. No unapplied-cash concept exists.
*Files:* `src/lib/ar.ts:184-237`, `src/lib/ap.ts:185-235`, `src/components/accounting/ReceiptForm.tsx`, `PaymentForm.tsx`.

*Time:* ~3 hours.
*What could break:* A genuine overpayment now has to be split into an applied receipt plus an on-account receipt. That is the correct handling, but tell the bookkeeper before it changes under them.

**C-3. `PATCH /api/purchase-orders/[id]` will rewrite a posted PO.**
*What is wrong:* `api/purchase-orders/[id]/route.ts` accepts `total` as `String(body.total)` with no numeric check, `status` with no enum check, and `lineItems` with no shape check. It can force a PO to `received` without receiving anything, or rewrite unit costs after the receipt already posted at the old cost.
*Files:* `src/app/api/purchase-orders/[id]/route.ts`; and `src/app/purchase-orders/[id]/page.tsx:10-36` for the same gap in `saveDraft`.

*What could break:* Any script or integration currently PATCHing POs loosely. I found no in-repo caller (`UNVERIFIED` for anything outside this repo).

**C-4. `deletePart` has no permission check and destroys FIFO cost layers.**
*What is wrong:* `src/app/inventory/page.tsx:40-46` — no role guard, and the Delete button renders for every role (`:331-337`). `part_receipts` and `part_cost_history` cascade (`src/db/schema.ts:271,283`), so the inventory subledger loses value while GL 1200 keeps its debit. *Files:* `src/app/inventory/page.tsx:40`, `src/app/vendors/page.tsx:27`, `src/app/vehicles/page.tsx:73`, `src/app/packages/page.tsx`.
*Smallest safe fix:* Add `canDelete(session)` to all four actions, matching what the sibling API routes already do. For parts specifically, refuse the delete outright when any `part_receipts` row exists and point the user at Archive instead.

*What could break:* Nothing legitimate. Archive already exists as the correct path (`archivePart` at `inventory/page.tsx:48`).

**C-5. `customers.tax_exempt` is read by no tax logic.**
*What is wrong:* The flag is captured (`crm/page.tsx:28`, `crm/[id]/edit/page.tsx:32`, `api/customers/route.ts:35`) and displayed (`crm/[id]/page.tsx:320`, `crm/page.tsx:133`), and **no** tax or invoicing code path consults it. A tax-exempt government sale can be taxed with nothing objecting.
